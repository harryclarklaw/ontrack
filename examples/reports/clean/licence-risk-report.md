## Methodology

- Each component's licence is read from the SBOM. The concluded licence is preferred over the declared licence where both are present.
- Licence strings are parsed as SPDX expressions, including AND, OR and WITH operators, using the SPDX licence list.
- Each licence is mapped to a category and a ship-posture by the policy file. For a dual (OR) licence the least restrictive branch governs by default, because the distributor may elect it; for an AND every licence applies and the most restrictive governs.
- Licences that are NOASSERTION, absent, or not recognised are never treated as acceptable by default. They are surfaced as unresolved or unknown and given the policy's conservative default posture.
- Project exceptions, where supplied, are applied after classification and are listed with their justification, owner and date.
- Every result records the policy rule that produced it, so each classification can be audited.

## Limitations

- This tool does not perform static or dynamic linkage analysis. Weak-copyleft obligations (for example LGPL or MPL) depend on how a component is linked, which must be assessed by a human.
- It classifies licences; it does not read the full licence text or detect additional terms embedded in a component.
- It is not a vulnerability scanner. Where the SBOM already contains vulnerability data it is surfaced for information only.
- It does not assert compliance with the EU Cyber Resilience Act or any other regulation, and is not a certification. It is a readiness and analysis aid.
- Its conclusions are only as good as the SBOM it is given. Components missing from the SBOM are invisible to it.
